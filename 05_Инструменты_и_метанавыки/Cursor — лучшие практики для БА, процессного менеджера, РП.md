# Cursor — лучшие практики для БА, процессного менеджера, РП

> Руководство по использованию Cursor для бизнес-аналитиков, процессных менеджеров и руководителей проектов — **без навыков программирования**.  
> Фокус: мышление, документы, координация, а не написание кода.

---

## 1. Думайте о Cursor как о «коллеге с доступом к вашим материалам»

Главная сила — не генерация текста, а **контекст**: агент видит файлы проекта, может их создавать, структурировать, сравнивать версии, искать противоречия.

**Практика:** заведите в workspace папки вроде:

- `docs/` — требования, BRD, протоколы встреч
- `processes/` — описания AS-IS / TO-BE
- `templates/` — шаблоны user story, RACI, чеклисты
- `data/` — выгрузки, CSV (без чувствительных данных)

Чем больше «источник правды» лежит в проекте, тем точнее ответы.

---

## 2. Выбирайте режим под задачу

| Режим | Когда использовать |
|-------|-------------------|
| **Ask (только чтение)** | «Объясни этот документ», «найди противоречия», «сделай summary встречи» — когда менять файлы не нужно |
| **Plan** | Большая задача с вариантами: «как описать процесс закупки», «как разбить эпик на stories» — сначала план, потом действие |
| **Agent** | «Создай шаблон», «обнови все user stories по новому формату», «собери one-pager из трёх файлов» |

**Правило:** для анализа и вопросов — Ask; для структурных решений — Plan; для артефактов — Agent.

---

## 3. Промпты для нетехнических ролей — конкретика важнее «умности»

**Плохо:** *«Напиши требования к системе»*

**Хорошо:**

```
Контекст: [роль, продукт, ограничения]
Вход: @docs/meeting-notes-2026-07-09.md
Задача: выделить 5–7 функциональных требований в формате «Как [роль], я хочу…, чтобы…»
Ограничения: не придумывай то, чего нет во входе; помечай [ASSUMPTION]
Выход: markdown-таблица с колонками ID, Requirement, Priority, Open Questions
```

### Полезные приёмы

- указывать **формат выхода** (таблица, чеклист, RACI, BPMN-текст)
- просить **явно помечать допущения** `[ASSUMPTION]`
- просить **открытые вопросы** отдельным блоком
- давать **пример** желаемого результата (1 строка — уже сильно помогает)

## 4. Rules — «корпоративная память» агента

**User Rules** и **Project Rules** (`.cursor/rules/`) — это постоянные инструкции:

- как называть артефакты (User Story vs Требование)
- какой шаблон user story принят в команде
- терминология (клиент / заказчик / контрагент)
- язык документов (RU/EN)
- что нельзя делать (не выдумывать сроки, не менять scope без пометки)

**Практика для РП:** одно правило вида *«Всегда добавляй секции: Scope, Out of Scope, Risks, Dependencies»* — и каждый документ будет единообразным.

Подробнее про rules/skills: [[Cursor — как усилить работу (skills, rules, harness)]].

## 5. Canvas — для «тяжёлых» аналитических артефактов

Когда нужны **таблицы, сравнения, таймлайны, матрицы рисков, интерактивные сводки** — Canvas удобнее длинного чата. Это отдельная панель с живым документом.

### Хорошие сценарии

- сравнение вариантов процесса (AS-IS vs TO-BE)
- матрица стейкхолдеров / RACI
- backlog grooming — группировка stories по эпикам
- post-mortem / ретро — структурированный разбор

---

## 6. @-упоминания — ваш главный инструмент контекста

- `@файл` — конкретный документ
- `@папка` — весь контекст папки
- `@web` — актуальная справка (стандарты, регуляторика)
- `@docs` — документация (если подключена)

**Практика:** в одном запросе связывайте 2–3 источника:

*«Сравни @processes/as-is.md и @docs/requirements-v2.md, найди расхождения»*

---

## 7. MCP-интеграции — мост к рабочим системам

Если в компании подключены MCP-серверы (Jira, Linear, Slack, Notion и т.д.), агент может:

- подтянуть задачи/тикеты
- сформировать статус-репорт
- подготовить draft комментария в тикет

**Для РП:** «Собери статус по эпику X: что done, что blocked, что на ревью» — при наличии интеграции это экономит 30–60 минут в неделю.

---

## 8. Automations — для повторяющихся ритуалов

Automations в Cursor — сценарии по расписанию или триггеру:

- еженедельный digest по папке `docs/meetings/`
- проверка, что все stories имеют DoD
- напоминание обновить RAID-log

Имеет смысл автоматизировать только **стабильные, повторяющиеся** процессы.

---

## 9. Типовые сценарии по ролям

### Бизнес-аналитик

- декомпозиция эпика → user stories + acceptance criteria
- gap-анализ: «что в требованиях не покрыто процессом»
- подготовка вопросов к интервью со стейкхолдерами
- нормализация разрозненных заметок в единый BRD

### Процессный менеджер

- описание процесса в текстовом BPMN-подобном формате
- поиск узких мест и handoff-ов между ролями
- чеклисты внедрения изменения процесса
- сравнение «как должно быть» vs «как описано в регламенте»

### Руководитель проектов

- статус-репорты из протоколов и заметок
- RAID-log из рассыпанных упоминаний рисков
- agenda + decision log для встреч
- коммуникации для стейкхолдеров (executive summary vs technical detail)

## 10. Организация работы с агентом (мета-практики)

1. **Один workspace = один проект/инициатива** — не смешивать контексты.
2. **Версионируйте документы** (git или даты в именах файлов) — агент лучше сравнивает `requirements-v1` и `v2`, чем «последнюю версию в голове».
3. **Итеративно:** сначала черновик → потом «ужесточи критерии» → потом «проверь на противоречия с @файл».
4. **Human-in-the-loop:** агент готовит draft, вы утверждаете — особенно для scope, сроков, обязательств.
5. **Фиксируйте удачные промпты** в [[Cursor — как усилить работу (skills, rules, harness)]] — это ваша личная библиотека.

---

## 11. Антипаттерны (чего избегать)

- Давать агенту задачу без контекста и формата выхода
- Хранить всё только в чате — чат не заменяет файлы проекта
- Принимать цифры (сроки, бюджет, объёмы) без пометки «проверить»
- Пихать в workspace конфиденциальные данные без политики безопасности
- Ожидать, что агент «знает» вашу компанию — это нужно явно описать в rules или документах

---

## 12. С чего начать (предложенные сценарии)

Можно по очереди прогнать практические сценарии:

1. Создать шаблон user story + rule под ваш формат
2. Загрузить протокол встречи → получить decisions + action items
3. Описать процесс AS-IS → TO-BE с gap-анализом
4. Собрать статус-репорт из нескольких файлов
5. Попробовать Canvas для матрицы стейкхолдеров
